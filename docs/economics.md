# Недорогое решение: выбирать график по энергии и последствиям опозданий

Для Кокшетау-1 ↔ Нурлы Жол предлагается связать расписание с рекомендациями
скорости и выбирать допустимый план по понятной денежной оценке. Первый прототип
работает локально на существующем компьютере. Расчёт использует Python, NumPy
и открытый OR-Tools; обучение нейросети, платный API и GPU для него не требуются.

Это известные методы. Наш вклад для хакатона — реализация на выбранном коридоре,
проверка сбоев и выбор плана с явными экономическими допущениями. Проценты Wabtec
и годовые показатели SBB не являются прогнозом для КТЖ. Заявление Wabtec относится
к топливу; в нашей модели рассчитывается электрическая энергия.

## 1. Формула выбора плана

Для каждого поезда считаем положительное конечное опоздание:

```text
D_i = max(0, arrival_i - due_i) / 3600  [поезд·ч]
```

Условная стоимость всего плана:

```text
J = price_kwh × E
  + passenger_delay_price × Σ D_passenger
  + freight_delay_price × Σ D_freight
```

Здесь `E` — тяговая и вспомогательная энергия, кВт·ч;
`price_kwh` — тг/кВт·ч; две другие ставки — тг за час опоздания одного поезда.
Они задают денежную оценку последствий задержек и должны быть согласованы
с заказчиком. Пассажирский поездочас не равен пассажиро-часу: загрузка вагонов
в текущих исходных данных отсутствует.

**J не равен бухгалтерским расходам или прибыли.** Для подтверждённой
себестоимости нужны реальные тарифы, расходы и договорные условия.
Энергетическая составляющая выводится отдельно от условных штрафов за задержку.

Перед сравнением стоимости выполняются независимая проверка плана и ограничения:

```text
Для каждого пассажирского поезда:
D_new_seconds <= D_reference_seconds + max_extra_passenger_delay_s

Дополнительно, если задан общий предел:
Σ D_new_seconds <= Σ D_reference_seconds + max_extra_total_delay_s
```

По умолчанию дополнительное пассажирское опоздание не допускается.
Опорный план также участвует в выборе: если улучшения нет, выбирается он.
При сбое опорный план обязан быть допустимым уже в новых условиях.
Минимум выбирается среди предоставленных кандидатов; глобальная оптимальность
всех возможных расписаний не утверждается.

### Как не посчитать экономию дважды

- Энергия разгона уже включена в `E`. Повторно добавлять «цену разгона» нельзя.
- Вспомогательная энергия ожидания и стоянок также уже включена.
- Для учёта использования локомотива и бригады нужна отдельная величина
  `H_i = (terminal_departure_i - release_i) / 3600` и ставка неэнергетических
  затрат. Опоздание `D_i` и время использования `H_i` — разные величины.
- Если стоимость ресурсо-часа включена отдельно, ставка последствий опоздания
  не должна повторно включать те же расходы.
- Износ, ремонты и закупку парка пока не переводим в тенге: подтверждённых
  зависимостей от режима движения нет.

## 2. Что показала симуляция после подключения railsim

Сохранённый прогон: восемь синтетических поездов, одинаковые маршруты и ограничения.
Энергия теперь использует коэффициенты Davis из `config/railsim.example.json`.
Это новая модель сопротивления, поэтому прежние значения энергии из упрощённого
расчёта не используются. CP-SAT при повторном запуске может выбрать другие планы.

| Вариант | Энергия, кВт·ч | Все опоздания, поезд·ч | Пассажирские опоздания, поезд·ч |
|---|---:|---:|---:|
| FCFS | 30 872,33 | 4,629 | 3,869 |
| balanced | 30 861,98 | 5,089 | 2,904 |
| passenger | 30 819,99 | 3,685 | 1,858 |
| eco | 26 520,37 | 11,389 | 7,071 |

Для денежного примера используются **учебные ставки**, не данные КТЖ:
50 тг/кВт·ч, 30 000 тг за пассажирский поездочас опоздания и 10 000 тг
за грузовой поездочас опоздания.

| Вариант | Условная стоимость J, тг | Допущен по пассажирским задержкам |
|---|---:|---|
| FCFS | 1 667 296,90 | Да |
| balanced | 1 652 079,40 | Да |
| passenger | 1 615 013,29 | Да |
| eco | 1 581 315,65 | Нет |

`eco` имеет меньшую денежную оценку, но ухудшает прибытие 5 пассажирских
поездов, максимум на 3758 с. При условии «не увеличивать положительное
опоздание ни одного пассажирского» он исключён.

Выбран `passenger`. Разница условной оценки относительно FCFS:
52 283,61 тг, из которых 2 616,94 тг относятся
к расчётной электроэнергии. Остальное — изменение условных штрафов за задержки.
Это не измеренная прибыль.

### Порог выгодности экономичного режима

При единой ставке опоздания λ:

```text
J = 50 × E + λ × Σ D_i
λ_break_even = сэкономленная стоимость энергии / дополнительные поездочасы опоздания
```

Для `eco` относительно FCFS в этом прогоне:

- экономия расчётной электроэнергии: 4 351,96 кВт·ч;
- условная экономия на энергии: 217 597,92 тг;
- дополнительное суммарное опоздание: 6,759 поездочаса;
- порог: примерно 32 192 тг за поездочас опоздания.

При большей ставке `eco` проигрывает по этой упрощённой формуле. Жёсткое
ограничение пассажирских задержек действует независимо от денежного выигрыша.
Опоздание нельзя подменять временем использования состава: для ресурсо-часов
нужен отдельный расчёт `H_i` из раздела 1.

## 3. Следующее улучшение: попадание в свободное окно

Если участок впереди освободится через 20 минут, а до него 20 км,
средняя скорость для попадания в это окно составляет:

```text
v_average = distance / time_to_window = 20 / (20 / 60) = 60 км/ч
```

На постоянных 80 км/ч поезд преодолел бы расстояние за 15 минут и затем ждал
пять минут. Предварительное согласование скорости может убрать это ожидание
перед сигналом. Это только арифметический пример: рабочий профиль должен учитывать
разгон, торможение, ограничения скорости, занятость ресурсов и следующие поезда.
Прогноз освобождения пути сам по себе не даёт разрешение на движение.

Для такой доработки планировщик должен выдавать окно `[earliest, latest]`,
а расчёт скорости минимизировать энергию внутри него. Условие отсутствия
конфликтов для поездов i и j на одном ресурсе:

```text
exit_i + clearance_i <= entry_j
либо
exit_j + clearance_j <= entry_i
```

В текущем прототипе все промежуточные остановки обязательны. Изменение числа
неплановых остановок пока не моделируется: для этого нужно отделить обязательные
остановки от проходных точек, описать блок-участки и согласовать граничные скорости
между соседними отрезками. Не следует заявлять экономию от устранённых остановок
по нынешнему расчёту `eco`.

Оценка энергии одного дополнительного разгона без рекуперации:

```text
E_acceleration ≈ mass_kg × (v_end_mps² - v_start_mps²) / (2 × efficiency × 3_600_000)
```

Для модельного грузового состава 2000 т, разгона с 0 до 60 км/ч и КПД 0,88
получается около 87,7 кВт·ч; для 6000 т — около 263 кВт·ч.
Результат зависит от массы и скорости. Это оценка кинетической составляющей,
без уклонов, сопротивления, возврата энергии при торможении и бортовых потребителей.

## 4. Запуск расчёта стоимости

После `python -m backend.app.cli simulate`:

```bash
python -m backend.app.cli economics --rates config/economics.example.json
```

Команда читает исходное движение из `output/corridor/normal` и FCFS из
`output/corridor/fcfs.json`, повторно проверяет планы и пересчитывает метрики.
Результаты:

- `output/corridor/economics.json` — ставки, отдельные составляющие стоимости,
  причины исключения, выбранный план и допущения;
- `output/corridor/economics_comparison.csv` — таблица для сравнения.

Программный интерфейс — `compare_plan_costs` в `backend/app/metrics/economics.py`.
Для сбоя ему передают соответствующее состояние, `previous` и допустимый
опорный план в том же состоянии. CLI-команда сейчас сравнивает исходный сценарий.

## 5. Что делает прототип недорогим

Для текущей симуляции используются имеющийся компьютер, локальные JSON/CSV
и библиотеки с открытым исходным кодом. OR-Tools распространяется по
[Apache 2.0](https://github.com/google/or-tools/blob/stable/README.md).
При наличии компьютера дополнительная покупка оборудования и лицензий
для этого прототипа не требуется. Работа разработчиков остаётся затратой.

Пилот на настоящей железной дороге потребует доступа к достоверным данным,
интеграции и испытаний; его стоимость пока не оценена. Связь, тарифы,
доступность устройств и станционные схемы необходимо подтвердить отдельно.

Окупаемость можно считать после измерения подтверждённого денежного эффекта:

```text
Net_month = confirmed_savings_month - support_and_operation_cost_month
Payback_months = implementation_cost / Net_month, если Net_month > 0
```

Умножать условную денежную оценку задержек J на 365 и объявлять её годовой
прибылью нельзя. Для прогноза нужны представительная нагрузка, одинаковые условия
сравнения, фактические ставки и измерения на нескольких сценариях.
