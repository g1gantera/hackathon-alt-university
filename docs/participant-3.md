# Твои задания: планирование, автоведение и метрики

Твой результат — пакет, который получает состояние участка
**Кокшетау-1 ↔ Астана Нурлы Жол**, выдаёт допустимый график, рекомендуемую скорость
и объяснимые показатели. Для грузовых поездов граница маршрута — Астана-1.

Ниже перечислено, что уже реализовано, что тебе нужно разобрать и проверить,
а что можно уточнить только после получения исходных данных.

## 1. Проверить данные участка

**Файлы:** [infrastructure.json](../data/corridor/infrastructure.json),
[sources.json](../data/corridor/sources.json),
[scenarios.py](../backend/app/scenarios.py).

**Уже реализовано:** связная геометрия OSM, 13 станций, 12 перегонов,
длина по карте 311,821 км. Наблюдения о путях сохранены отдельно от параметров
симуляции. Команда `audit` выдаёт недостающие сведения.

**Твои действия:**

1. Запусти `python -m backend.app.cli audit`.
2. Проследи порядок: Кокшетау-1 → Разъезд № 17 → Джемантуз → Курорт Бурабай →
   Жасыл → Макинка → Ельтай → Акколь → Шортанды → Тонкерис → Разъезд № 39 →
   Астана-1 → Нурлы Жол. Это узлы текущей модели.
3. Проверь для каждого перегона длину, ссылки OSM, `mapped_main_track_count`,
   `model_main_track_count` и `status`.
4. Объясни на защите происхождение `SIM-1` и `SIM-2`: это два принятых для расчёта
   станционных пути по 1500 м. Они не означают, что реальная станция имеет два пути.
5. Сохраняй `operational_exactness=false`, пока эксплуатационные данные не проверены.

**Критерий готовности:** для каждого значения ты можешь назвать источник
или указать, что это допущение. Первые десять перегонов имеют наблюдение двух
линий в срезах OSM; два последних требуют дополнительной сверки.

**Нужны данные:** ТРА станций — техническо-распорядительные акты, схемы маршрутов,
полезные длины путей, границы блок-участков и разрешённые направления движения.
Публичная карта не закрывает эти пункты. `--require-exact` показывает этот пробел.

## 2. Настроить воспроизводимую нагрузку

**Файл:** [scenarios.py](../backend/app/scenarios.py), функция `corridor_scenario`.

**Уже реализовано:** поезда `SYN-*` в обоих направлениях, приоритеты, масса,
длина, готовность к отправлению, целевое прибытие. Параметры нагрузки задаются
числом поездов и интервалом. Исходные данные не содержат случайной генерации.

**Твои действия:**

```bash
python -m backend.app.cli generate --trains 8 --interval 900
```

1. В `scenarios/kokshetau_nurly_zhol.json` выбери по одному пассажирскому
   и грузовому поезду. Найди их маршрут, `release_s`, `due_s` и `priority`.
2. Проверь, что грузовой не заезжает на пассажирский терминал Нурлы Жол.
3. Выбери базовую нагрузку для защиты. Для эксперимента увеличивай число поездов
   либо уменьшай интервал, сохраняя одинаковые параметры для всех стратегий.
4. В отчётах оставляй пометку `synthetic_forecast`.

**Критерий готовности:** повторный запуск генератора создаёт тот же набор поездов.
Числа нагрузки называются синтетическими; фактического графика КТЖ у команды нет.

## 3. Разобрать планирование

**Файлы:** [solver.py](../backend/app/planning/solver.py),
[common.py](../backend/app/planning/common.py),
[baseline.py](../backend/app/planning/baseline.py).

**Уже реализовано:** OR-Tools CP-SAT выбирает времена и доступные главные
и станционные пути. Он учитывает длину состава, направление движения, стоянки,
закрытия и буферы освобождения. Эвристика FCFS даёт исходный вариант для сравнения.

**Твои действия:**

1. Найди переменные прибытия, отправления и выбора пути.
2. Проследи, как `add_exactly_one` выбирает один допустимый путь, а
   `add_no_overlap` запрещает пересечение резервирований одного ресурса.
3. Сравни `balanced`, `passenger` и `eco`. Приоритет меняет цену задержки;
   обязательные ограничения остаются обязательными.
4. Проверь, что разные главные пути могут работать одновременно, а один путь
   не получает пересекающиеся резервирования.
5. Проверь, что модель не отправляет поезд на путь с запрещённым направлением.
6. Передавай предыдущий план при пересчёте после начала движения.

**Критерий готовности:** для выбранного поезда можешь объяснить назначенный путь,
время отправления и причину ожидания по резервированиям и ограничениям.

## 4. Проверить сценарии проблем

**Файлы:** [scenarios.py](../backend/app/scenarios.py),
[service.py](../backend/app/planning/service.py),
[validation/plan.py](../backend/app/validation/plan.py).

Начни с одного случая:

```bash
python -m backend.app.cli simulate --incidents main_track_closure --budget 5
```

| Сценарий | Что проверить в результате |
|---|---|
| `main_track_closure` | Ожидание открытия закрытого главного пути; соседний путь не получает автоматического разрешения встречного движения |
| `signal_failure` | Новые входы запрещены в интервале сбоя; уже начатые движения сохранены |
| `station_track_closure` | Выбран другой доступный станционный путь либо назначено ожидание |
| `train_delay` | Отправление после задержки на 30 минут и пересчёт следующих движений |
| `speed_restriction` | Ограничение 40 км/ч увеличивает время хода и меняет профиль скорости |
| `single_track_operation` | Второй путь допускает оба направления только после явного разрешения в сценарии; встречные движения разделены во времени |
| `ten_incidents` | Все десять ограничений учитываются в одном расчёте |

В `single_track_operation` разрешение обоих направлений сохраняется до конца
горизонта этого модельного состояния. `speed_restriction` задаёт ограничение
для сценария без автоматического восстановления скорости по таймеру.

Для каждого случая открой `output/corridor/<сбой>/resolution.json`:

1. Найди событие в `incident`.
2. Посмотри, какие нарушения возникли бы при сохранении старого графика:
   `violations_before`.
3. В `solutions` выбери вариант и найди изменённые времена и пути.
4. Проверь `metrics.applicable`, отсутствие нарушений и достижимость профилей.
5. Запиши `elapsed_ms` и `budget_exceeded`. Если вариант не найден,
   используй `diagnostics`; отсутствие результата нельзя объявлять решением.

**Критерий готовности:** можешь показать «ограничение → нарушение старого плана →
изменение графика → результат проверки» на конкретных значениях.

Дополнительно подключены 12 случаев из `railsim`: дефект рельса, хищение,
паводок, снег, песок, жара, отказ локомотива, дефект вагона, переезд,
происшествие с людьми, ремонтное окно и сход. Их имена в CLI начинаются
с `railsim_`. Подробная таблица и связь исходных файлов с нашей логикой —
в [railsim-integration.md](railsim-integration.md).

Минимум генератора — пять поездов, по умолчанию восемь. Проверь также
`python -m backend.app.cli realism --trains 5 --runs 3`: все прогоны должны иметь
одинаковый состав поездов и случайные события для сравниваемых политик.

## 5. Разобрать автоведение

**Файл:** [advisory/speed.py](../backend/app/advisory/speed.py).

**Уже реализовано:** профиль на пространственной сетке, ограничения скорости,
ускорения и торможения, подбор крейсерской скорости под назначенное время,
расчёт тяговой и вспомогательной энергии. Длинные перегоны рассчитываются
векторными операциями NumPy.

**Твои действия:**

```bash
python -m backend.app.cli simulate --incidents speed_restriction --profiles
```

1. Найди нужный профиль по ключу `поезд:перегон` в `solutions[].profiles`.
2. Сравни длительность профиля с `Movement.end_s - Movement.start_s`.
3. Проверь начальную и конечную скорость, ограничения и положительное время
   прохождения каждого отрезка.
4. Сравни обычный вариант с `eco`: изменились время, скорость и расчётная энергия.
   Не объявляй экономию, если итоговая энергия выросла.
5. Помни, что `time_s` и `position_m` локальны относительно начала перегона.

**Критерий готовности:** профиль физически достижим в принятой модели и согласован
с расписанием. При недостижимом времени возвращается `UNREACHABLE`.

**Нужны данные:** разрешённые скорости, уклон и кривые пути, характеристики
локомотива, тормозов и сопротивления состава. Сейчас остановка предусмотрена
на каждой станции, профиль пути ровный, рекуперация не учитывается.

## 6. Объяснить метрики и загрузку путей

**Файлы:** [metrics/quality.py](../backend/app/metrics/quality.py),
[metrics/load.py](../backend/app/metrics/load.py),
[config/metrics.json](../config/metrics.json).

**Уже реализовано:** конечные задержки, задержки пассажирских, точность прибытия,
выполнение графика, энергия, индекс и отдельная загрузка каждого пути.

**Твои действия:**

1. Открой `output/corridor/comparison.csv` и сравни варианты одного сценария.
2. В `<сценарий>/<стратегия>_track_load.csv` найди выбранный главный путь.
3. Объясни `occupied_s`, `closed_s`, `available_s`, `entry_blocked_s`, `load_pct`
   и `available_load_pct`: время занятости включает буферы освобождения.
4. Сравни количество проходов в направлениях `a_to_b` и `b_to_a`.
5. Во всех сравнениях сохраняй окно 0–43 200 секунд и одинаковые поезда.
6. Настрой и зафиксируй веса индекса, масштаб задержек и энергетический бюджет
   до итогового сравнения стратегий. Настройки хранятся в каждом результате.
7. Различай энергетический ориентир быстрых независимых профилей и проверенный
   график FCFS. Это разные базы сравнения.
8. Запусти `python -m backend.app.cli economics`. Открой `output/corridor/economics.json`:
   объясни ставки, причины исключения вариантов и выбор плана. Сравни отдельно
   стоимость электроэнергии и условные оценки задержек. Формулы и пример
   находятся в [economics.md](economics.md).

**Критерий готовности:** каждое число можно пересчитать по формулам из
[algorithms.md](algorithms.md), а недопустимый план не выдаётся за применимое решение.

## 7. Подготовить свою часть к передаче и защите

Передай пакет алгоритмов, сценарий, конфигурацию метрик и пример Python-вызова
из [README](../README.md). Вход — `Scenario` и при необходимости предыдущий `Plan`;
выход — планы, профили, метрики, время расчёта и диагностика.

Проверь:

- [ ] Данные карты и допущения подписаны, конечная точка — Нурлы Жол.
- [ ] Реальная нагрузка не приписана синтетическим поездам.
- [ ] Направления и разные главные пути учитываются отдельно.
- [ ] Начатое движение сохраняется при пересчёте.
- [ ] Каждый возвращённый вариант проходит независимую проверку.
- [ ] Профили скорости согласованы с длительностями движений.
- [ ] Все варианты сравниваются на одном наборе поездов и в одном окне.
- [ ] Статусы `INFEASIBLE`, `UNKNOWN`, `INVALID` объясняются корректно.
- [ ] Фактические замеры записаны в [verification.md](verification.md).

Краткий сценарий защиты: исходный график → закрытие пути → нарушение прежнего
плана → проверенное решение → скорость одного поезда → загрузка выбранного пути
и сравнение задержек/энергии. Заверши перечнем данных, которые нужны для перехода
от модели по карте к точной эксплуатационной модели.
