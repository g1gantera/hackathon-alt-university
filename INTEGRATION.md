# Объединённое приложение: era + M_part + logic

Ветка `integrated` объединяет три компонента на одном адресе:

- `era` — исходная карта сети, поиск станций и проверка маршрута;
- `M_part` — React-панель, API, авторизация, WebSocket и история;
- `logic` — планирование, профили движения, проблемы и метрики.

## Запуск

Из корня репозитория, Python 3.12+ и Node 22+:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements.lock.txt -e .
npx --yes pnpm@11.25.0 --dir frontend install --frozen-lockfile
npx --yes pnpm@11.25.0 --dir frontend build
python -m uvicorn integration.main:app --host 127.0.0.1 --port 8000
```

В PowerShell активация: `.\.venv\Scripts\Activate.ps1`.
Используйте один процесс Uvicorn: симуляция хранится в памяти сервера.

Откройте **http://127.0.0.1:8000**. Сверху доступны «Диспетчер» и «Карта сети».
В панели можно запускать движение, вводить сбои, рассчитывать и применять планы.
На карте кнопка «К маршруту» приближает Кокшетау — Нурлы Жол; восемь маркеров
получают позиции из того же сервера. Запуск и пауза на карте управляют общей
симуляцией. Переключение экранов не создаёт новый набор поездов.

Параметры `.env.example` сохранены. Для `.env` добавьте `--env-file .env` к Uvicorn.
Авторизация общая: при `DEMO_MODE=false` вход выполняется через «Диспетчер»,
карта использует ту же cookie. Роль viewer не может запускать движение.

## Как связаны компоненты

Общая оболочка находится в `integration/`. Подключение расчётов расширено в backend;
новые модули: `backend/app/live_logic.py` и `backend/app/logic_api.py`.
`map.html`, `map_data.js`, `network.json` и исходные алгоритмы не редактировались.
Два изменения frontend ограничены согласованными привязками данных и подписями.

```text
Общая страница /
  ├─ /dispatcher/ → существующая React-панель
  └─ /network/    → существующая карта era + отдельный слой поездов
            │
        /api/* и /ws
            │
      существующий backend M_part
            │
      адаптер native logic
            │
      планы, ограничения, профили, метрики
```

- `integration/main.py` запускает lifecycle backend ровно один раз и монтирует
  приложение backend с прежними адресами API и WebSocket.
- `integration/static/index.html` переключает два исходных интерфейса во фреймах
  на том же origin, поэтому авторизация и состояние общие.
- `map-bridge.js` подписывается на `/ws`, читает `/api/topology` и показывает
  фактическое состояние этой симуляции поверх карты. Он не рассчитывает движение.
- Дополнительный скрипт вставляется только в HTTP-ответ `/network/`.
  Сам файл `map.html` сохранён; `/map.html` отдаёт его исходную версию.
- `/network.json` отдаёт оригинальный граф era, включая подозреваемые разрывы.
  Он не заменяет эксплуатационные ограничения logic: такой переход изменил бы
  алгоритмы и допущения модели. Для позиций поездов используется геометрия backend.
- При потере WebSocket карта обозначает последнее состояние и переподключается.
  Вход в панели становится доступен карте без отдельного аккаунта.

Прямые адреса: `/dispatcher/`, `/network/`, `/map.html`, `/docs`, `/api/integration`.
Исходный запуск `uvicorn backend.app.main:app` по-прежнему доступен.

## Подключение logic к живой симуляции

- По умолчанию работает `DISPATCH_ENGINE=logic`: восемь синтетических поездов,
  два направления Кокшетау — Нурлы Жол. Грузовые заканчивают маршрут на Астана-1,
  как в исходной модели.
- CP-SAT рассчитывает три варианта. Сбой приостанавливает часы до применения
  проверенного плана. Начатые движения сохраняются. Если во время расчёта добавлен
  следующий сбой, устаревший результат отбрасывается и расчёт повторяется.
- Движение берётся из native-профиля с постоянным ускорением в каждой ячейке.
  Энергия учитывает тягу по расстоянию и вспомогательное питание по времени,
  включая ожидание на станции, перед входом на участок и помощь неисправному поезду.
  После завершения всех стоянок сумма совпадает с native-прогнозом.
- Индекс использует пять компонентов из `config/metrics.json`. Два существующих
  регулятора интерфейса распределяют суммарный вес задержки и энергии (0,5).
  Остальные веса сохранены: пропускная способность 0,2, конфликты 0,15,
  точность прибытия 0,15. До первого прибытия фактический индекс предварительный
  (`metrics.provisional=true`), неизвестный компонент исключается с нормированием.
  Приоритеты поездов округляются до целых не ниже 1; API возвращает принятые значения.
- Состояние каждого главного и станционного пути выводится из native-ограничений.
  Скоростное ограничение действует на вход в указанный интервал. Существующее
  поле `section.status` сохраняет словарь фронтенда; частичное закрытие имеет
  `partial_closure=true`, точное состояние находится в `sections[].tracks[]`.
- После изменения ограничений прежний прогноз помечается `applicable=false`.
  Отчёты загрузки и экономики отвергают недействительный план. Исторический прогноз
  до сбоя не используется для расчёта экономии в новых условиях.

Дополнительные методы доступны в `/docs`, с общей авторизацией:

| Метод | Назначение |
|---|---|
| `GET /api/logic/diagnostics` | Текущий сценарий, native-план, свежая проверка и прогноз |
| `GET /api/logic/metrics` | Фактические и прогнозные пять компонентов, настройки |
| `GET /api/logic/track-load?start_s=0&end_s=43200` | Загрузка каждого пути в заданном окне |
| `GET /api/logic/economics/rates-example` | Явно учебные ставки для примера |
| `POST /api/logic/economics` | Сравнение доступных планов по переданным ставкам |
| `POST /api/logic/realism` | Отдельный эксперимент railsim: 1–10 прогонов, заданный seed |

Тело экономики: `{"reference_plan_id":"<id>","rates":{...}}`.
Опорный план должен быть допустимым сейчас; после сбоя можно выбрать один из
новых вариантов. Выбор экономически предпочтительного варианта не применяет его
автоматически. Денежные величины — оценки модели при явно заданных ставках.

Тело эксперимента: `{"runs":1,"seed":42}`. Он использует исходный коридор с восемью
поездами и общими случайными событиями для baseline/auto, а не текущее расписание
живой симуляции. Ответ содержит `scope=offline_baseline_corridor`,
`applied_to_live=false`. Временные файлы удаляются; существующий `output/` не меняется.
Расчёты выполняются локально, внешние платные сервисы не подключены.

Согласованные правки фронтенда показывают расстояние из logic, полный расход энергии,
предварительный индекс до первых прибытий и скрывают недействительный профиль.
В настройках поясняются веса пяти компонентов. Дополнительные подробности доступны
через API; новых экранов загрузки и экономики не добавлено.

## Контейнер

Дополнительные файлы оставляют исходный Dockerfile и Compose без изменений:

```bash
docker compose -f docker-compose.yml -f compose.integrated.yml up --build
```

Или без Compose:

```bash
docker build -f Dockerfile.integrated -t railflow-integrated .
docker run --rm -p 127.0.0.1:8000:8000 railflow-integrated
```

## Проверки

После сборки frontend:

```bash
python -m pytest backend/tests tests integration/tests -q
node --test integration/tests/coordinates.test.mjs
```

Для запущенного локального сервера:

```bash
python -m integration.smoke
```

Smoke-проверка сбрасывает тестовую симуляцию, запускает поезда, создаёт закрытие,
получает новые планы по WebSocket, применяет проверенный план и снова сбрасывает
симуляцию. Исходные записанные результаты в `docs/` и `output/` она не меняет.

Обновление подключения logic: проверены **215 Python-тестов** (полный набор и
повтор затронутых проверок после последних изменений), **3 JavaScript-теста**,
проверка типов и production-сборка frontend. В браузере проверены пояснение весов,
подписи индекса/энергии и нулевое расстояние обратного грузового поезда до отправления.
При внесении сбоя уже открытый старый профиль скрывается, даже если ID активного
плана ещё не изменился; проверенный вариант успешно применяется из интерфейса.
Живой API/WebSocket-тест: восемь поездов, три плана за **4,742 с**, применение
проверенного плана после закрытия, совпадение API с native-планом и экспорт CSV.
Пятисекундный бюджет — цель расчёта; фактическое превышение возвращается в
`within_budget=false`. Часть бюджета оставлена на подготовку ответа и передачу
между процессами. Сборка нового Docker-образа для этого обновления не выполнялась.

Первоначальное объединение, 1 октября 2026: **185 Python-тестов**, **3 JavaScript-теста** и production-сборка
frontend прошли. Живой тест получил три плана за 4,875 с, применил один и проверил
совпадение плана API с native-планом logic. В браузере проверены карта с восемью
поездами, управление движением и переход между двумя экранами.
Образ `Dockerfile.integrated` также собран и запущен: тот же smoke-тест прошёл
в контейнере на Python 3.12, три плана получены за 4,888 с. Тестовый контейнер
после проверки остановлен. Compose-плагин локально не установлен; контейнер
проверялся через `docker build` и `docker run`.

GitHub Actions для этого объединения не смог выделить runner: аккаунт владельца
репозитория заблокирован из-за проблемы с оплатой. Сообщение GitHub:
`The job was not started because your account is locked due to a billing issue.`
[Запуск проверки](https://github.com/g1gantera/hackathon-alt-university/actions/runs/36847923321).
Приведённые выше успешные результаты получены локально.

Геометрия остаётся из OSM, нагрузка синтетическая. Реальные ограничения путей,
вероятности происшествий и параметры тяги не появились при объединении веток.
Исходная карта использует внешний Leaflet CDN и подложки OSM/CARTO; для них
нужен интернет. Все прежние допущения модели сохранены.
